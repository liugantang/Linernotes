# AI 音乐播放器 — 分阶段开发计划

> 版本 0.1 · 2026-09-25 · 对应需求文档 [REQUIREMENTS.md](REQUIREMENTS.md)
> 估时按 **1 名全职开发者** 计算，单位为“周”，仅供排期参考。

## 总览

```
阶段  0  工程基建                         ─┐
阶段  1  播放内核（libmpv）                  │
阶段  2  曲库扫描与数据库                    ├─ M1：能用的本地播放器（已开始记录播放日志）
阶段  3  基础 UI                            │
阶段  4  播放日志 + 系统集成                ─┘
阶段  5  AI 基础设施                        ─┐
阶段  6  管家 I：乱码修复 + 艺人归一 + 审核    ├─ M2：AI 管家（最先对用户有实际价值的 AI 能力）
阶段  7  管家 II：补全 / 版本 / 重复 / 写回   ─┘
阶段  8  自然语言查询 I（元数据 + 行为）      ── M3：可对话的曲库
阶段  9  音频理解：选型评测 + 实现           ─┐
阶段 10  自然语言查询 II（声音 + 情绪曲线）   ─┴ M4：听得懂声音
阶段 11  向导：歌词 / 翻译 / 百科 / 深挖     ─┐
阶段 12  主持人：私人电台 DJ                 ─┴ M5：电台感
阶段 13  档案员：统计 / 叙事 / 瞬间          ── M6：记忆
阶段 14  打磨、跨平台、发布                  ── 1.0
```

**排序理由**

1. **播放日志必须最早上线**（阶段 4）：档案员、行为查询、DJ 的“你上次听是半年前”都依赖历史数据，越早记录，后面功能上线时越有料。
2. **管家先于其他 AI 功能**：NL 查询、DJ、叙事全都建立在干净的元数据上，脏数据会让后面每个功能都显得很蠢。
3. **向导先于 DJ**：DJ 串场里的“创作背景”直接复用向导的事实缓存，避免 DJ 自己编造。
4. **音频理解是最大技术不确定项**：方案不预设（CLAP 只是候选之一），建议在阶段 5 期间抽 2–3 天先搭好评测集并粗测候选方案（见 9.1–9.2），不要等到阶段 9 才发现效果不够。

**贯穿全程的约定**

- 详细的流程、代码与测试规范见 [DEVELOPMENT.md](DEVELOPMENT.md)；每个编号任务完成即提交一次。

- 每个阶段结束：可运行的构建 + 测试通过 + 更新本文件中的状态。
- 数据库 Schema 变更一律通过迁移脚本（阶段 2 建立机制）。
- 所有 LLM 调用都经过阶段 5 的统一客户端，禁止在功能代码里直接发请求。

## 阶段 1：播放内核（1.5 周）✅ 完成（2026-09-26）

**目标**：一个无界面也能稳定工作的播放引擎。

| # | 任务 |
|---|---|
| ✅ 1.1 | `MpvHandle`：RAII 封装 `mpv_handle`，初始化参数（`vid=no`、`audio-display=no`、`gapless-audio=weak`、`replaygain` 等） |
| ✅ 1.2 | 事件循环接入：`mpv_set_wakeup_callback` → `QMetaObject::invokeMethod(Qt::QueuedConnection)` → 在主线程 drain 事件 |
| ✅ 1.3 | 属性观察：`time-pos`、`duration`、`pause`、`volume`、`idle-active`、`playlist-pos`，转换为 Qt 信号 |
| ✅ 1.4 | `Player` 类（QObject，Q_PROPERTY 暴露给 QML）：play/pause/stop/seek/volume/mute |
| ✅ 1.5 | `PlayQueue` 模型：队列由我们自己维护（而非完全依赖 mpv playlist），向 mpv 预加载下一首以实现 gapless |
| ✅ 1.6 | 播放模式：顺序/列表循环/单曲循环/随机（实现“不短期重复”的洗牌：Fisher-Yates + 最近历史回避） |
| ✅ 1.7 | 错误处理：文件不存在、解码失败 → 跳过并上报 |
| ✅ 1.8 | 输出设备枚举与切换（`audio-device-list` / `audio-device`） |
| ✅ 1.9 | 为 DJ 预留：`VoiceChannel`（第二个 mpv 实例专门播放语音）+ 主通道音量平滑渐变（ducking）接口，先实现接口与简单测试 |
| ✅ 1.10 | 队列与进度持久化（退出保存，启动恢复） |
| ✅ 1.11 | 单元/集成测试：用测试音频文件验证 gapless 切换、seek、事件时序 |

**交付物**：`player` 库 + 一个命令行测试程序（传入若干文件即可顺序播放）。
**验收**：连续播放一张 gapless 专辑无缝隙；长时间播放（4 h）无内存增长；ducking 渐变无爆音。

**验收记录（2026-09-26）**：
- gapless：用 playcli 播放一张现场专辑（namie amuro LIVE STYLE 2014，96 kHz FLAC），人工试听，曲目交界处无停顿、无咔哒声；自动测试 `gaplessTransitionDoesNotStop` 验证切换期间不进入 Stopped、两首 1 s 曲目总耗时无额外间隙
- 4 h 内存：`scripts/soak-player.sh tests/fixtures/audio 4`（`ao=null`、列表循环、5 个 1–5 s 素材含一个坏文件，约 1 万次切换）。RSS 96.4 MB → 114.2 MB，前几分钟一次性上涨约 14 MB，之后增速递减，2.5 h 后走平（最后 1.5 h 在 114.2–114.3 MB），判定无持续增长
- ducking：playcli 的 `d <gain> [ms]` 命令人工试听 300/500/50 ms 渐变，无爆音；另用 `ao=pcm` 录音确认 `af-command` 实际改变输出电平（峰值 0.125 → 0.012）
- ctest：18 个测试在 debug / ci（-Werror）/ asan 下全部通过；格式检查通过
- GitHub Actions：合并后首次运行失败（clang-tidy 未通过；gcc 下 tst_player_Player 偶发超时，原因是无音频服务的容器中设备枚举在 libpipewire 中死锁），修复后全部通过（2026-09-26，run 36216292698）
- 与计划的偏差：1.5 拆为 PlayQueue 模型与 Player 集成两个提交；1.1–1.3 合为一个提交；ducking 采用 lavfi volume 滤镜 + `af-command`，不改用户音量。已知局限：gapless 且前后音频格式不同时，滤镜链重建到重新应用增益之间可能有极短的全音量窗口；在曲目切换瞬间修改队列可能多一次切换（状态随后自愈）

## 阶段 2：曲库扫描与数据库（2 周）

## 阶段 6：管家 I — 乱码修复 + 艺人归一 + 审核界面（2.5 周）

**目标**：解决最常见、最痛的两个问题，并建立“AI 提议 → 用户审核”的通用工作流。

| # | 任务 |
|---|---|
| 6.1 | **乱码检测**：识别 mojibake 特征（大量 Latin-1 补充区字符如 `Ã`、`Ö`、`¸`，或 `?` 占位） |
| 6.2 | **乱码规则修复**：把字符串回编码为 Latin-1 原始字节，再尝试 GBK / Big5 / Shift-JIS / EUC-KR / UTF-8 解码；用 uchardet + 字符频率打分选最优；同专辑内的曲目共享编码判断以提高准确率 |
| 6.3 | 不可逆损坏（已变成 `???`）的处理：用文件名、目录名、指纹匹配（阶段 7）兜底，标记为“需在线补全” |
| 6.4 | 疑难项交 LLM：把候选解码结果 + 上下文（同专辑其他曲目、文件路径）发给 LLM 选择/修正 |
| 6.5 | **艺人归一——候选聚类**：规则层（大小写/全半角/空格/标点规范化、简繁转换、拼音/罗马字相似度）+ MusicBrainz 艺人别名查询 |
| 6.6 | **艺人归一——LLM 判定**：对候选簇让 LLM 判断“是否同一人”并给出推荐显示名与各语言名；避免误合并同名不同人（结合专辑、年代上下文） |
| 6.7 | 艺人实体化：写入 `artists` + `artist_aliases`，`track_artists` 指向实体；显示名偏好设置（原文/简体/英文） |
| 6.8 | 多艺人拆分（F-BUT-03）：分隔符规则 + 已知组合名白名单 + LLM 判别 |
| 6.9 | **通用审核界面**：变更批次列表 → diff 表格（字段、旧值、新值、置信度、理由、来源）；按字段/按置信度筛选；全选接受、逐条编辑、拒绝；接受后刷新 effective 层 |
| 6.10 | 变更日志与撤销：每批次可整体撤销 |

## 阶段 9：音频理解 — 选型评测 + 实现（3 周）

**目标**：让系统“听见”音乐，满足 F-AUD 需求，全部在本地完成。**不预设模型，先用评测选型。**

需求 → 所需能力 → 候选方案：

| 需求 | 需要的能力 | 候选方案 |
|---|---|---|
| “慢歌”“安静/燥”、情绪曲线 | BPM、响度、energy、valence | 信号特征（libebur128、BPM 估计）+ 情绪回归/分类模型 |
| “有小号和鼓机” | 乐器多标签识别 | 专用乐器分类模型（如 Essentia 的 MTG-Jamendo 系列）或 CLAP 类零样本打分 |
| “是不是纯音乐” | 人声检测 | 人声/器乐分类模型 |
| “多来点像这首的” | 相似度 | 任意音频嵌入（分类模型的中间层嵌入即可） |
| 任意文字描述找歌（P2） | 文本-音频共同空间 | CLAP 类模型（LAION-CLAP、MS-CLAP 等） |

| # | 任务 |
|---|---|
| 9.1 | **评测集（建议提前到阶段 5 并行）**：从自己曲库中挑约 200 首，人工标注乐器、人声/纯音乐、energy/valence 大致档位；再准备 30 条声音类查询及期望结果 |
| 9.2 | **候选粗测**：优先用 Python 快速跑各候选方案，对照评测集比较准确率、速度（CPU 每首耗时）、模型体积、许可证；输出选型结论文档。可以是**组合方案**（例如：信号特征 + 分类模型满足 P1，文本-音频模型只为 P2 的自由描述检索服务） |
| 9.3 | **部署路线验证**：选定模型导出 ONNX，C++ 侧用 ONNX Runtime 跑通并与 Python 结果比对；若 C++ 路线成本过高（前处理、tokenizer、算子支持），改用 Python sidecar 进程（本地 HTTP/stdin 通信） |
| 9.4 | 音频解码管线：FFmpeg 解码 → 按所选模型的要求重采样/转单声道 → 分段（跳过开头静音，每首取若干片段） |
| 9.5 | 信号特征：EBU R128 响度与响度范围（libebur128）、BPM、调性（Camelot 表示）、动态范围 |
| 9.6 | 模型推理：乐器/人声/情绪等标签分数写入 `audio_tags`；嵌入向量（如有）float16 存入 `embeddings` |
| 9.7 | 派生维度：**energy**、**valence** 归一化到 0–1（信号特征与模型输出融合，权重用评测集调） |
| 9.8 | 相似度检索：内存索引（余弦相似度暴力搜索，SIMD 优化），10 万首 < 50 ms；预留 sqlite-vec 接口 |
| 9.9 | 后台调度：低优先级线程、CPU 占用上限、仅空闲时运行选项、断点续跑、进度展示；模型版本变更时可增量重算 |
| 9.10 | GPU 执行器（可选）：CUDA / ROCm / DirectML / CoreML EP 自动探测 |
| 9.11 | “相似歌曲”：歌曲右键 → 找相似（F-AUD-05） |
| 9.12 | 调试视图：某首歌的特征与 Top 标签，用于人工检查效果；允许用户手动纠正标签 |

**验收**：选型结论有评测数据支撑；1 万首分析在普通 CPU 上可在一晚内完成；评测集上乐器标签（小号、钢琴、鼓机等明显特征）准确率 ≥ 70%，人声/纯音乐 ≥ 90%；“相似歌曲”主观评测可用。

## 主要风险与应对

| 风险 | 影响 | 应对 |
|---|---|---|
| 候选音频模型效果不足或 C++ 部署困难 | 阶段 9–10 延期 | 需求驱动的评测集先行；多方案组合（分类模型 + 信号特征 + 可选文本-音频模型）；Python sidecar 备选 |
| 自由文本描述检索（F-AUD-04）做不好 | 部分声音查询只能走标签 | 该项定为 P2；P1 的乐器/情绪/能量需求用分类模型即可满足 |
| LLM 在艺人归一上误合并 | 数据被污染 | 默认进审核队列；三层元数据 + 批次撤销 |
| DJ/向导编造事实 | 信任崩塌 | 只允许引用检索到的事实；标注来源；用户反馈“事实错误”入口 |
| 用户自带 Key 的调用开销 / 本地小模型能力不足 | 批量整理慢或贵、结果差 | 规则层优先、缓存、批处理；显示用量预估；为本地模型准备更简单的 prompt 和更强的 JSON 容错 |
| 本地中文 TTS 质量 | DJ 体验打折 | 提供云端高质量选项；跟进开源中文 TTS |
| MusicBrainz 对华语/日韩内容覆盖不足 | 补全率低 | 文本匹配 + LLM 兜底；后续可评估其他数据源 |
