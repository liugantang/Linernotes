# 开发规范

> 适用于本仓库的所有代码与文档，包括人工编写和 AI 辅助生成的内容。
> 相关文档：[需求](REQUIREMENTS.md) · [开发计划](ROADMAP.md)
> AI 协作分工（Claude 规划与审查、Gemini 执行）见仓库根目录的 `CLAUDE.md`；代码由审查者在审查通过后提交。

## 1. 开发流程

### 1.1 以任务为单位推进

[ROADMAP.md](ROADMAP.md) 中每个编号任务（如 `2.6`）就是一个最小工作单元：

1. 开始前：确认任务的范围与验收标准；不清楚就先补充到 ROADMAP 里，不要边做边扩大范围。
2. 实现：代码 + 对应的单元测试一起写。
3. 自检：满足 [1.3 提交前检查清单](#13-提交前检查清单)。
4. **提交**：每个编号任务完成后必须提交一次。任务较大时可以拆成多个提交，但每个提交都要能编译、测试通过。
5. 在 ROADMAP 中把该任务标记为完成（见 1.4）。

不允许：一个提交混杂多个不相关的任务；把“顺手改的无关代码”塞进功能提交。确实需要的顺手修改，单独提交。

### 1.2 分支

- `main`：始终保持可编译、测试全绿。
- 阶段分支：`phase/<编号>-<简称>`，如 `phase/02-library`。一个阶段的所有任务在阶段分支上逐个提交。
- 阶段完成、满足阶段验收标准后，合并回 `main`（`--no-ff`，保留阶段边界），并打标签：
  - 普通阶段：`phase-02`
  - 里程碑：`m1`、`m2` …；正式版本：`v1.0.0`
- 临时实验（如技术验证）：`spike/<主题>`，结论写进文档后分支可删除，实验代码不直接合入。

### 1.3 提交前检查清单

- [ ] 能在 Debug 与 Release 下编译，无新增警告
- [ ] `ctest` 全部通过
- [ ] 已运行 `clang-format`；`clang-tidy` 无新增问题
- [ ] 新增/修改的逻辑有对应测试（见第 4 节）
- [ ] 涉及数据库结构的改动有迁移脚本（见 5.1）
- [ ] 涉及用户可见行为的改动，已手动运行程序验证过
- [ ] 没有提交密钥、个人路径、调试残留（`qDebug` 打桩、注释掉的大段代码）

### 1.4 阶段收尾

每个阶段结束时，额外做以下事情，然后再合并：

1. 逐条核对该阶段的 **验收标准**，把结果（数据、截图或结论）记录在 ROADMAP 该阶段末尾。
2. 在 ROADMAP 中标注阶段状态：`✅ 完成（2026-xx-xx）`；任务行前加 `✅`。
3. 若实现与需求/计划有偏差，同步修改 REQUIREMENTS / ROADMAP，并在提交说明中写明原因。
4. 更新 `CHANGELOG.md`（从 M1 开始维护）。

### 1.5 提交信息

采用 [Conventional Commits](https://www.conventionalcommits.org/) 格式，描述用中文：

```
<type>(<scope>): <简述，不超过 50 字>

<可选正文：为什么这么做、重要的取舍、关联的任务编号>

Refs: ROADMAP 2.6
```

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 仅测试相关 |
| `docs` | 仅文档 |
| `build` | 构建系统、依赖 |
| `ci` | CI 配置 |
| `chore` | 其他杂项 |

`scope` 使用模块名：`player`、`library`、`db`、`ui`、`ai`、`butler`、`nlq`、`audio`、`guide`、`dj`、`archive`。

示例：`feat(library): 读取标签时保留 Latin-1 原始字节`

## 2. 代码规范（C++）

### 2.1 基本约定

- 标准：**C++20**。可以用 `std::optional`、`std::span`、`std::variant`、concepts、`<ranges>`；暂不使用 modules 和 coroutines。
- 格式：以仓库根目录的 `.clang-format` 为准（基于 Qt/WebKit 风格，4 空格缩进，行宽 100）。**不要手动争论格式，交给工具。**
- 静态检查：以 `.clang-tidy` 为准；确需豁免时用 `// NOLINT(<检查名>)` 并写明原因。
- 编译警告视为错误（CI 中 `-Werror`）。

### 2.2 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 类、结构体、枚举类型 | PascalCase | `PlayQueue`、`TrackId` |
| 函数、方法、变量 | camelCase | `loadTracks()`、`trackCount` |
| 成员变量 | `m_` 前缀 | `m_queue` |
| 静态成员 / 全局常量 | `s_` 前缀 / `k` 前缀 | `s_instance`、`kMaxRetries` |
| 枚举值 | PascalCase（使用 `enum class`） | `PlayMode::RepeatOne` |
| 命名空间 | 小写 | `aimusic::library` |
| 文件名 | 与主类同名 | `PlayQueue.h` / `PlayQueue.cpp` |
| Qt 属性 / 信号 | 遵循 Qt 习惯 | `Q_PROPERTY(int volume ...)`、`volumeChanged()` |
| QML 文件 | PascalCase | `PlayerBar.qml` |

### 2.3 头文件与依赖

- 头文件使用 `#pragma once`。
- include 顺序：对应头文件 → 本项目 → Qt → 第三方 → 标准库，各组之间空一行（由 clang-format 自动排序）。
- 头文件中能前向声明就不 include；第三方库（mpv、TagLib、FFmpeg、ONNX Runtime）的头文件**只允许出现在对应封装模块的 .cpp 中**，不外泄到公共头文件。

### 2.4 模块边界

```
app / qml  →  features/*（butler, nlq, dj, guide, archive）  →  ai / audio / library / player  →  core
```

- 只允许依赖箭头右侧（更底层）的模块，禁止反向和横向依赖；需要跨模块通信时通过接口或信号。
- **UI（QML）不直接访问数据库和网络**，只通过暴露给 QML 的 C++ 模型与服务对象。
- 所有大模型调用必须经过 `ai` 模块的统一客户端，功能代码中不允许自己发 HTTP 请求给 LLM。
- 每个模块一个 CMake 目标（静态库），依赖关系在 CMake 中显式声明，以便编译期就发现越界依赖。

### 2.5 内存与资源管理

- 默认使用 RAII：`std::unique_ptr` 表达独占所有权；仅在确实共享时用 `std::shared_ptr`。
- QObject 对象使用 Qt 父子关系管理生命周期；不要对有 parent 的 QObject 再套智能指针。
- 禁止裸 `new`/`delete`（QObject 带 parent 的 `new` 除外）。
- C 库句柄（`mpv_handle*`、`AVFormatContext*` 等）必须用 RAII 包装（自定义 deleter 的 `unique_ptr`）。

### 2.6 错误处理

- 预期内的失败（文件不存在、网络超时、模型返回格式错误）用返回值表达：`std::optional<T>` 或 `std::expected<T, Error>`（若编译器不支持则用项目内的 `Result<T>`）。
- 不使用异常作为控制流；第三方库抛出的异常在封装边界处捕获并转换。
- 错误要带上下文：`Error{code, message, detail}`，日志中能定位到哪个文件/哪次请求。
- 用户可见的错误走统一的通知机制，不直接弹 `QMessageBox`。

### 2.7 线程

- 主线程只做 UI 与轻量逻辑；扫描、解码、音频分析、网络结果处理等耗时操作放到后台（`QThreadPool` / `QtConcurrent` / 专用 `QThread`）。
- SQLite：每个线程独立连接；写操作集中在单个写线程/队列，批量事务提交。
- 跨线程只通过信号槽（`Qt::QueuedConnection`）或线程安全队列传数据；共享可变状态必须加锁并在注释中说明保护关系。
- mpv 回调中不做任何实际工作，只投递到 Qt 事件循环。

### 2.8 日志

- 每个模块定义自己的 `QLoggingCategory`，如 `aimusic.library`。
- 级别：`qCDebug` 调试细节；`qCInfo` 关键流程节点；`qCWarning` 可恢复的问题；`qCCritical` 功能不可用。
- **日志中禁止出现 API Key、完整的用户瞬间内容**；LLM 请求/响应完整内容只在开发者模式下记录。

### 2.9 注释与文档

- 注释说明“为什么”，不复述“做了什么”。
- 公共接口（模块对外头文件）写简短的 Doxygen 风格注释：用途、参数约束、线程安全性、所有权。
- 非显而易见的算法（乱码修复打分、曲线选歌代价函数等）在代码旁写清思路，或链接到 `docs/` 下的设计说明。

### 2.10 QML

- QML 只负责展示与交互，业务逻辑放在 C++；QML 中的 JavaScript 仅限简单的展示逻辑。
- 组件拆分：单个 QML 文件不超过约 300 行，超过就拆组件。
- 颜色、字号、间距统一来自主题单例（`Theme.qml`），不写死数值。
- 所有用户可见文字使用 `qsTr()`。

## 3. 数据与隐私规范

- **原始标签只读**：扫描结果写入 `raw_tags` 后不再被修改；所有修正走 `corrections` / `user_overrides`（见需求 4.2）。
- **写文件是显式操作**：只有“写回文件”功能可以修改用户的音频文件，且必须先备份。其他任何代码不得写用户的音乐目录。
- **音频不出本机**：任何网络请求中不得包含音频数据。
- 发往 LLM 的数据必须经过 `PrivacyGuard` 过滤。
- 测试与示例数据中不使用真实的个人信息。

## 4. 单元测试规范

### 4.1 框架与组织

- 框架：**Qt Test**（与 Qt 信号、事件循环集成最好），通过 `ctest` 运行。
- 目录结构与源码对应：

```
tests/
  unit/<模块>/tst_<类名>.cpp      # 单元测试，每个类一个测试文件
  integration/<主题>/tst_*.cpp    # 集成测试（真实数据库、真实 mpv、多模块协作）
  fixtures/                       # 测试素材：小音频文件、乱码样本、LLM 录制响应
  benchmarks/                     # 性能基准，不在普通 ctest 中运行
```

- 测试类命名 `Tst<类名>`，测试函数命名描述行为：`fixesGbkMojibakeInTitle()`、`skipsUnreadableFileAndContinues()`。
- 数据驱动测试使用 Qt Test 的 `_data()` 函数，覆盖多组输入。

### 4.2 什么必须有测试

| 类型 | 要求 |
|---|---|
| 纯逻辑（解析、转换、规则、算法） | **必须**有单元测试，覆盖正常路径、边界和错误输入。例如：乱码修复、艺人名规范化、多艺人拆分、LRC 解析、查询 DSL → SQL 编译、曲线选歌器、洗牌算法 |
| 数据库迁移 | 每个迁移脚本都要测试：从上一版本迁移后数据正确 |
| 修复缺陷 | **先写一个能复现缺陷的失败测试**，再修复 |
| 与外部服务交互（LLM、MusicBrainz、天气） | 用录制回放测试（见 4.4），不在单元测试中访问真实网络 |
| UI | 不强制单元测试；关键交互流程在阶段验收时手动验证。复杂的 C++ 模型类（如 `TrackListModel`）需要测试 |

覆盖率不设硬性百分比，但 `core`、`library` 以及各 feature 模块中的规则/算法代码应接近全覆盖。

### 4.3 测试的写法

- **独立**：每个测试自己准备数据，不依赖执行顺序；数据库使用内存 SQLite 或临时目录（`QTemporaryDir`）。
- **确定**：不依赖当前时间、随机数、网络。时间通过可注入的 `Clock` 接口获取；随机数使用可设种子的生成器。
- **快速**：单个单元测试应在 100 ms 内完成；慢测试放入 integration 并加标签，可单独运行。
- **只测行为**：通过公共接口测试，不为了测试而暴露私有成员。
- 断言信息要能说明问题：优先 `QCOMPARE`（会打印实际值和期望值），而不是 `QVERIFY(a == b)`。
- 异步逻辑使用 `QSignalSpy` + `QTRY_COMPARE`，禁止用固定时长 `sleep` 等待。

### 4.4 AI 相关测试

- **录制回放**：`ai` 模块提供录制模式，把真实请求/响应保存为 `tests/fixtures/llm/*.json`；测试中使用回放客户端。录制文件中不得包含 API Key。
- **规则层与 LLM 层分开测**：规则层用确定性单元测试；LLM 层测试的是“把模型输出解析、校验、落库”的代码，而不是测模型本身。
- **评测集**（与单元测试区分）：NL 查询、乱码修复、艺人归一、音频标签等有独立的评测集与评测脚本（`tools/eval/`），用于换模型或改 prompt 后的质量回归，输出准确率报告。评测需要真实模型，不放进 CI 必跑项。
- 修改 prompt 模板时，在提交说明中附上评测结果的前后对比。

### 4.5 测试素材

- 音频素材尽量小（几秒钟），使用自己生成的或明确可自由分发的音频，并在 `tests/fixtures/README.md` 中记录来源。
- 真实曲库中的“怪样本”（奇怪编码、损坏文件）只提取标签部分做成最小复现样本，不提交受版权保护的完整音频。

## 5. 其他约定

### 5.1 数据库迁移

- 结构变更只能通过新增迁移脚本：`resources/migrations/NNNN_<描述>.sql`，编号递增，**已合入 main 的迁移脚本不得修改**。
- 迁移在事务中执行；失败时回滚并提示用户，不留下半升级状态。
- 升级前自动备份数据库文件。

### 5.2 依赖管理

- 新增第三方依赖前评估：许可证与 GPL-3.0 兼容、维护活跃度、Linux 发行版是否有包。
- 在 `docs/DEPENDENCIES.md` 中登记依赖名称、用途、许可证、最低版本。

### 5.3 Prompt 模板

- Prompt 模板放在 `resources/prompts/<功能>/<名称>.md`，不在 C++ 代码中硬编码长文本。
- 模板头部注明版本号、用途、输入变量、期望输出格式（JSON Schema 的路径）。

### 5.4 文档

- 设计决策（选型、重要取舍）记录在 `docs/decisions/NNNN-<标题>.md`，简短写明背景、选项、结论。例如阶段 9 的音频理解选型。
- 需求或计划变化时，同步修改 REQUIREMENTS / ROADMAP，不让文档和代码脱节。
