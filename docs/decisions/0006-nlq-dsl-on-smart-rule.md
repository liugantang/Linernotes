# 0006 · 自然语言查询：DSL 扩展智能歌单规则，LLM 单次结构化输出

> 2026-10-01 · 阶段 8 开工前。

## 背景

阶段 8 要把“我去年冬天循环最多的那几首”“收藏了但从没听完的专辑”这类问句变成本地查询，并把 LLM 的理解显示为可编辑的条件标签（F-NLQ-07），修改后本地重跑（8.7）。

现有代码里已经有一套“条件 → SQL”的机制：智能歌单的 `SmartRule`（字段 / 运算符 / 值的条件列表，匹配全部或任一，参数化 SQL，白名单字段，JSON 持久化，QML 条件编辑器）。

## 决定

1. **查询 DSL 以 `SmartRule` 为核心扩展，而不是另起一套**。
   - `SmartRule` 增加播放行为与新元数据字段：播放次数、跳过次数、听完次数、平均完成度、最后播放时间、版本类型、语言、所属专辑/艺人已收藏、所属专辑完成度；日期字段增加绝对区间（`yyyy-MM-dd`，本地时区，含两端）。
   - 规则级增加可选的**播放时间窗口**（`playedFrom` / `playedTo`）：设置后播放次数类字段按窗口内的 `play_events` 统计，否则用 `track_play_stats` 的累计值。
   - 自然语言查询 `nlq::Query` = 结果实体（曲目 / 专辑 / 艺人）+ `SmartRule`（曲目级条件）+ 排序键 + 数量。专辑 / 艺人结果由命中的曲目聚合而来；“专辑已收藏”“专辑完成度”这类专辑级条件表达为曲目的“所属专辑…”字段，不需要 HAVING。
   - 好处：只有一个编译器要做白名单与注入防护；条件标签与智能歌单编辑器共用控件；“存为动态智能歌单”（F-NLQ-10）以后几乎免费。
2. **语言不入库**：由标题、专辑名、艺人名的文字种类推断（含假名 → 日语，含谚文 → 韩语，含汉字 → 中文，只有拉丁字母 → 西文），注册为 SQLite 自定义函数在查询时计算，不加迁移。
   已知局限：只有汉字的日文歌会判为中文；不足时再考虑按艺人多数票修正。
3. **LLM 用法仍是单次结构化输出，不做工具调用循环**。
   - 8.4 的 `search_library(dsl)` 实现为结构化输出（JSON Schema 即 DSL），程序拿到 DSL 后本地执行，不把结果回传给模型。
   - 8.8 多轮追问无状态：请求里带上“上一条 DSL + 新的一句话”，模型输出新的完整 DSL；不保存对话记录、不做上下文管理。
   - 8.5 实体消歧：模型只输出它理解的名字；程序在本地艺人 / 别名表里匹配，匹配不上或有多个时由界面反问，用户选择后本地改写条件，不再调用模型。
   - 真正的多工具、多轮 agent 需求留到 11.7（深挖对话），届时再讨论是否引入外部 agent。
4. **排序键属于 `nlq::Query`，不扩展 `TrackSortKey`**：曲目列表的分页排序依赖键集分页与索引，加入“窗口内播放次数”这类动态排序代价大；NLQ 结果有数量上限，直接 ORDER BY ... LIMIT。

## 影响

- 智能歌单编辑器要能编辑新字段（枚举字段用下拉框，日期区间用两个日期输入，播放窗口）。
- 评测（8.11）以 DSL 等价为准：给定固定的“今天”与时区，比较模型输出与期望 DSL 的条件集合、实体、排序与数量。
