# 0003 · 艺人署名由 LLM 解析，规则只做机械工作

> 2026-09-28 · 阶段 6 返工

## 背景

[0002](0002-butler-design.md) 第 3 条定下“规则优先、LLM 只处理疑难项”。落到艺人归一与拆分上，规则不只是省 token，还**决定了 LLM 能看到什么**：

- 合并候选只来自三条规则路径：规范化后精确相同、罗马字词元相同、编辑距离为 1；外加 MusicBrainz 按名字/别名精确命中。LLM 只确认编辑距离为 1 的名字对。
- 拆分只认内置分隔符（feat.、×、&、、、/ …），括号内一律不看。

结果是规则没想到的写法 AI 根本没机会判断。例：`高垣彩陽` 与 `高垣彩陽（as 雪音クリス）`、`高坂穂乃果(CV. 新田恵海)` 与声优本人都没有进入任何候选。阶段 6 的评测也显示，不查 MB 时召回只有 24%，漏掉的 `아이유` / `IU`、`방탄소년단` / `BTS`、`苏打绿` / `Sodagreen` 恰恰是 LLM 凭知识就能认出、而规则永远写不全的。继续逐个格式补规则（`as`、`CV`、`from`、`starring`…）只会让规则越来越多，覆盖面仍然有限。

## 决定

1. **原则**：艺人相关的判断（这个署名里是谁、要不要拆、是不是同一人）全部交给 LLM；规则只做机械工作：文本规范化、按键分组、结果校验、生成修正。本决定取代 0002 第 3 条中关于艺人的部分和第 6 条；乱码修复仍然是规则优先（规则层是确定性的，准确率已达标）。

2. **署名解析**（新任务 `butler.artist_credit`，在曲库整理中位于乱码修复之后、艺人合并之前）：
   - 输入：`effective_metadata` 中 `artist`、`album_artist` 的去重字段值，每批约 100 个值调用一次 LLM。
   - 输出（结构化，每个值一项）：`performers`：真正的演唱者或团体列表，每项有 `name`（按标签原文写法，不翻译、不转繁简）和 `aka`（模型确信的其他语言名、罗马字、常见写法，可为空）；`roles`：署名中的角色、标注等附带信息（只记录，不作为艺人）；`confidence`、`reason`。
   - 角色署名一律归到演唱者：`高垣彩陽（as 雪音クリス）` → `高垣彩陽`；`高坂穂乃果(CV. 新田恵海)` → `新田恵海`；多位演唱者 → 多项。组合名（`Simon & Garfunkel`、`Wake Up, Girls!`）保持一项。这些只以提示词中的示例说明，代码里没有任何格式规则。
   - 结果存入新表 `artist_credits`（字段值为主键，外加 JSON 结果、模型、提示词版本、时间）。按值缓存，以后只解析新值；模型或提示词版本变化时可以重跑。
   - 当 `performers` 的 `name` 用 `" / "` 连接后与原值不同时，产出曲目字段修正（沿用现在拆分修正的形式：`artist` / `album_artist` 字段、旧值、新值、置信度、理由）。它同时取代原来的多艺人拆分：`CorrectionKind` 新增 `ArtistCredit`，原 `artist_split` 的分隔符规则、提示词和 schema 删除，旧批次仍可查看和撤销。原值始终保留在 `raw_tags` 中，角色名写进理由。

3. **合并候选：按身份键分组**（纯代码，线性复杂度，不两两比较）：
   - 每个艺人实体的身份键 = 自身名字的 `exactKey`，加上所有解析结果中 `name` 与该实体名相同的演唱者的 `name` 与 `aka` 的 `exactKey`；启用 MusicBrainz 时，再加上 MB 匹配到的艺人名与别名。
   - 有共同键的实体用并查集并成一组。
   - 名字本身还有待署名修正的实体（解析结果与原值不同，修正尚未接受）不参与合并，由第 2 步处理；接受后下一次运行自然会进入分组。
   - 删除罗马字词元（`romanTokens`）与编辑距离（Fuzzy）两条规则路径。错别字、罗马字变体、姓名顺序颠倒都由第 2 步的 `aka` 覆盖。

4. **组内确认**（LLM，每组一次调用）：输入各成员的名字、曲目数、专辑样本、解析得到的 `aka`，启用 MB 时附上 MB 匹配信息（名字、别名、消歧说明）。输出把组分成若干“同一实体”子集，每个子集带 `confidence` 与 `reason`，不同的人留在各自的子集里。确定子集之后，规范实体选择、别名修正、MB 各语言别名沿用现有逻辑。只由原名 `exactKey` 相同连起来、且名字不短的组（繁简、大小写、标点差异）不经 LLM，直接提议，与现状一致；这也是未配置 AI 时仍然能用的部分。组的成员数设上限，超出时说明键发生了冲突，记日志并跳过该组。

5. **MusicBrainz 的角色**：从单独的匹配路径改为身份键来源（第 3 步）和确认证据（第 4 步），召回能力保留，最终判断统一由 LLM 做。

## 影响

- 新迁移 `0013`：`artist_credits` 表。
- 删除：`ArtistSplit` 的分隔符规则与 `ArtistSplitLlm`、`romanTokens`、`ArtistCluster` 中的罗马字与 Fuzzy 路径、合并任务的 `fuzzy` / `mb` 条目类型、`artist_split` 的提示词与 schema。`ArtistMergeLlm` 从“成对确认”改为“按组确认”。
- 曲库整理的步骤变为：乱码修复 → 署名解析 → 艺人合并。体检报告中“多艺人字段”一项改为“待解析署名 N 个”；“疑似重复艺人”按已缓存的解析结果分组计数。
- token 用量：真实曲库（1466 个字段值）首次全量解析估计 8～10 万 token，之后只有增量；阶段 6 验收中“规则层先处理掉绝大部分”的前提不再成立，改为度量“首次全量 + 增量”。
- 测试：分组、构造请求、把结构化结果转成修正都是纯函数，用 JSON 字面量做单元测试；LLM 部分用录制回放。`tools/eval` 新增署名解析语料（`as`、`CV`、feat.、组合名、括号注释等），艺人合并语料重跑，与阶段 6 的记录对比：误合并率仍需 < 1%，不查 MB 的召回应明显高于 24%。

## 修订（2026-09-28）：曲库整理不再查 MusicBrainz

6.15 按第 5 条实现后做了语料评测（157 个名字、78 对应合并的名字，deepseek-v4.1-flash）：不查 MB 召回 100%、查 MB 96%～100%，误合并都是 0；LLM 凭知识给出的 `aka` 已能覆盖 `아이유` / `IU`、`王靖雯` / `王菲` 这类情况。MB 限速每秒 1 次，真实曲库两千多个艺人要查 40 分钟以上，评测中还出现过十几分钟无结果的情况。收益小、代价大，因此撤掉：

- 删除 `butler.mb_lookup` 步骤、合并确认中的 MB 证据、MB 外语别名提议与“查询 MusicBrainz”开关；身份键只来自实体名与署名解析的 `aka`。
- 同时删除只为此服务的 `MusicBrainzClient` 与艺人搜索解析。阶段 7 做指纹与专辑匹配时按录音 / 发行查询的需要重新实现（旧代码见提交 c2f9d67）。
- 保留 `CorrectionSource::MusicBrainz` 枚举值与 `mb_cache` 表（前者是已持久化的值，后者在已发布的迁移中）。
- 失去的是 MB 提供的各语言别名；显示名偏好（原文 / 简体 / 英文）改为依赖解析得到的 `aka`。
