# 0005 · 专辑信息补全改由 LLM 完成，撤掉 MusicBrainz；封面按需从 iTunes 查

> 2026-10-01 · 阶段 7 返工。取代 [0004](0004-musicbrainz-album-matching.md)。
> **修订（同日）**：第 2 条的 LLM 专辑信息补全实测后撤销，见文末“修订”。第 1、3 条维持。

## 背景

0004 用 MusicBrainz 文本搜索按专辑匹配 release，补年份、专辑艺人、音轨号/碟号、总数、乱码标题与封面。实际使用中：

- **慢**：MB 限速 1 次/秒，每张专辑约 4 次请求，真实曲库 1520 张待补专辑首轮约 100 分钟。
- **不稳定**：MB 经常 503 / 超时；匹配还依赖候选选择与打分（7.4c 为此返工过一次），发行版本多时仍会挑到与本地文件不同的版本。
- 阶段 6 已经因为同样的原因撤掉过 MB 艺人查询（[0003](0003-artist-credit-by-llm.md) 修订）。

按信息来源看，MB 补的字段大多不需要联网：

| 字段 | 主要来源 |
|---|---|
| 音轨号、碟号、总音轨数、总碟数 | 文件名（`03. xxx`）、目录名（`CD2`、`Disc 2`）、同目录文件数与编号 |
| 专辑艺人 | 各曲艺人是否一致、目录名 |
| 年份 | 目录名常带 `(1999)`；否则靠模型知识 |
| 无法修复的乱码标题 | 模型结合同专辑其他曲目、文件名推断 |
| 封面、MBID | LLM 给不出 |

本地证据推出的编号描述的正是用户手上这份文件，反而比从 MB 选一个 release 更准。

## 决定

1. **撤掉 MusicBrainz 与 Cover Art Archive**：删除 `MusicBrainzClient`、`AlbumMatch`、`MbMatch*`、`CoverArt*` 及其表（`mb_cache`、`mb_album_matches`、`mb_track_matches`）。
   MBID 不再记录；版本识别与重复识别不依赖它。历史批次中的 `mb_match` 修正仍可查看与撤销（保留枚举与显示名）。
2. **专辑信息补全**（新任务 `butler.album_info`）：以专辑为单位，把专辑名、专辑艺人、目录路径与每首曲目的文件名、标题、艺人、时长、现有编号交给 LLM，
   返回缺失字段的值，每个值带**证据来源**：
   - `path` / `tags`：由文件名、目录名或其他曲目的标签推出；
   - `knowledge`：来自模型知识（主要是年份和乱码标题原文）。
   模型不确定时返回空，不要猜。**只补空字段**，生成修正提议（`CorrectionKind::AlbumInfo`，来源 LLM）。
   `knowledge` 来源的提议**一律不自动接受**，不论置信度与阈值，理由中注明“来自模型知识，未经核实”。
   每次请求可包含多张专辑（按曲目数分批），结果按专辑记录已检查，之后只处理新增或变动的专辑。
3. **封面**：默认只用本地封面（内嵌、目录图片）。专辑详情对没有封面的专辑提供“在线查找封面”：
   用户点击后用 iTunes Search API（无需 key）按“专辑名 + 专辑艺人”在几个地区商店（tw、hk、jp、us；国区不可用）搜索，
   含汉字时另用繁体写法再搜一次，列出候选缩略图，由**用户选择**后下载 1400×1400 图，作为 `source='online'` 的封面。
   不做批量下载：iTunes 限速约 20 次/分钟、排序不可靠（实测搜 `pink floyd dark side` 找不到原专辑，简体 `周杰伦 范特西` 排第一的是《依然范特西》），
   由用户挑选即可容忍匹配误差；接口本意是推广 iTunes 商店，个人少量使用可以接受，批量抓取不合适。

## 后果

- 专辑补全不再依赖外部服务的限速，速度取决于 LLM 并发与批大小；需要配置 LLM 服务（原 MB 补全不需要）。
- 冷门专辑的年份可能没有或需要用户审核；没有封面的专辑需要用户逐张手动查找。
- 散曲（没有专辑名）也能按文件名推断编号，但年份多半补不出。

## 修订（2026-10-01）：撤销 LLM 专辑信息补全

7.14 实现后用真实曲库副本实测：

- **缺的主要是年份，而年份大多没有本地证据**：缺年份的 1029 张专辑中，只有 93 张的目录名带年份，728 张与其他专辑混放在同一目录（如 `ハイレゾアニソング/`），只能靠模型记忆。
- **模型记忆不稳定**：同一批 16 张专辑跑 4 次，`シューゲイザー` 分别给出 2015 / 2023 / 2014 / 2018，`azure` 给出 2019 / 2018 / 2015，Walküre Trap! 两次分别为 2016 / 2017。这些值只能进审核，而用户审核时也无从判断。
- **慢且费 token**：输出以思考为主（每 16 张专辑约 2 万输出 token、约 60 秒）；Ollama Cloud 并发 8 时总吞吐只有单请求的约 2 倍；reasoning effort 调到 low 只省约 25%。1520 张待补专辑约 260 万 token、45 分钟以上。
- 除年份外能从本地推出的字段（专辑艺人、音轨号）缺得少，不值得为此调用 LLM。

决定：移除 `butler.album_info` 与整理页“补全专辑信息”步骤（7.17）。**元数据补全暂不提供**；MusicBrainz 仍不接回。
以后若重做，应以可靠的数据源为准，LLM 不作为事实（年份、曲目表）的来源。
