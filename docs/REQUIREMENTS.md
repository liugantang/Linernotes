# AI 音乐播放器 — 需求规格说明

> 版本 0.1 · 2026-09-25
> 技术栈：C++20 / Qt 6 (Qt Quick + QML) / libmpv
> 定位：**免费开源**（GPL-3.0-or-later）、**本地优先**的桌面音乐播放器。AI 不替代曲库，而是让曲库「变干净、能对话、会主持、可解读、有记忆」。

---

## 0. 术语

| 术语 | 含义 |
|---|---|
| 曲目 (Track/Recording) | 一个具体的音频文件所对应的录音 |
| 作品 (Work) | 同一首歌的抽象概念，下挂多个版本（录音室版 / Live / Remaster / Acoustic / Remix…） |
| 原始标签 (Raw Tags) | 从文件中读到的标签，只读、永不在 DB 中被覆盖 |
| 生效元数据 (Effective Metadata) | 原始标签 ⊕ 自动修正 ⊕ 用户覆写 三层合并后的结果 |
| 播放事件 (Play Event) | 一次播放行为的完整记录（开始、结束、实际时长、是否跳过、来源） |
| 瞬间 (Moment) | 用户给某首歌绑定的生活记忆 |
| LLM 服务 | 任意兼容 OpenAI Chat Completions 接口的服务，由用户自己填写地址、Key 和模型名 |
| 音频理解 (Audio Understanding) | 在本地从音频中提取可检索信息（特征、标签、向量等）的能力，具体模型不预设 |

## 1. 产品原则（贯穿所有需求）

1. **本地优先与隐私**：音频文件永不上传；发给云端 LLM 的只有文本元数据与聚合统计，且用户可逐项关闭。软件不内置任何 Key、不提供中转服务；用户自带 OpenAI 兼容服务（云端或 Ollama / llama.cpp 等本地服务均可）。
2. **非破坏性**：任何 AI 修改先进入「待审核」或「覆写层」，写回文件是显式操作，且可撤销、有备份。
3. **LLM 理解意图，本地负责执行**：LLM 不直接“挑歌”或“写 SQL 改库”；它输出结构化意图 / 计划，由本地确定性代码执行。这保证结果可解释、可复现、成本可控。
4. **可解释**：AI 做出的每个判断（合并艺人、识别版本、生成歌单）都要能看到“为什么”。
5. **可降级**：断网或没有配置 API Key 时，播放器作为一个普通的好用播放器完整可用。
6. **事实与创作分离**：DJ 串场、音乐解读中涉及的事实，必须标注来源或以“据说/可能”措辞；无可靠来源时不编造。

## 4. 关键技术方案（需求层面的约束）

### 4.1 技术选型

| 领域 | 选型 | 说明 |
|---|---|---|
| 语言/构建 | C++20、CMake、vcpkg 或系统包 | Linux 下直接用系统包 |
| UI | Qt 6 Quick/QML（Qt 6.8+），C++ 模型暴露给 QML | 列表用 `QAbstractListModel` |
| 播放 | libmpv client API（纯音频，无需 render API），`mpv_set_wakeup_callback` 接入 Qt 事件循环 | |
| 标签 | TagLib 2.x | 读写 |
| 编码检测 | uchardet + ICU（转码、简繁、拼音辅助） | |
| 数据库 | SQLite（QtSql 或直接 sqlite3）、FTS5；向量先用内存暴力检索，规模大时再上 sqlite-vec | 10 万 × 512 维 float ≈ 200 MB，可用 float16/int8 量化 |
| 指纹 | Chromaprint + AcoustID API + MusicBrainz API | |
| 音频分析 | FFmpeg（解码/重采样）、libebur128（响度）、BPM/调性算法（自实现或 Essentia/aubio） | |
| 音频理解 | 待阶段 9 评测决定。候选：CLAP 类文本-音频模型；Essentia 预训练分类模型（乐器/情绪/流派）；传统特征（响度/BPM/频谱）。推理倾向 ONNX Runtime | 备选：Python sidecar 进程 |
| LLM | 自研轻量 OpenAI 兼容客户端（QNetworkAccessManager + SSE） | 不引入重型 SDK |
| TTS | 云端 HTTP API；本地 sherpa-onnx / Piper | |
| 密钥 | QtKeychain | |
| 系统集成 | Qt DBus（MPRIS2） | |

### 4.2 元数据三层模型

```
raw_tags (只读，扫描写入)
   └─ auto_corrections (AI/规则生成，带来源、置信度、状态: pending/accepted/rejected)
        └─ user_overrides (用户手动修改，最高优先级)
= effective_metadata (视图/物化表，UI 与查询只读这一层)
```

### 4.3 NL 查询架构

```
用户输入 → LLM(工具调用) → Query DSL(JSON) → 校验 → 编译为 SQL(+向量检索) → 结果
                                              ↑
                                    UI 显示为可编辑条件标签
```
- LLM 看到的是 DSL Schema 与曲库的“概要信息”（流派列表、艺人数、时间范围），不是整个曲库。
- 情绪曲线：LLM 输出 `{duration, keypoints:[{t, energy, valence}], constraints}`；本地规划器用加权代价（曲线偏差 + 过渡平滑 + 多样性 + 用户偏好）做 beam search 选歌。

### 4.4 DJ 管线

```
当前曲目开始播放
  → 确定下一首（队列）
  → 上下文构建（元数据、向导事实缓存、上次播放时间、时间/天气、人设）
  → LLM 生成串场词（长度受控）
  → TTS 合成 → 音频缓存
  → 当前曲目剩余 N 秒时，按混音策略调度语音 + ducking
```

## 5. 范围之外（当前版本不做）

- 流媒体服务接入（Spotify/Apple Music 等）
- 移动端
- 在线社交/分享社区
- 音频生成（AI 作曲）
- 多用户账户与云同步（P2 之后再评估）
- 任何收费功能、内置 API Key、中转服务
- OpenAI 兼容协议以外的 LLM 接口（主流服务和本地推理框架基本都提供兼容端点）

## 6. 已确定的决策

| 问题 | 决定 |
|---|---|
| LLM 提供商 | 不设默认，用户自行填写；只需兼容 OpenAI 接口 |
| 商业模式 | 免费开源，无付费功能 |
| 音频理解方案 | 不绑定 CLAP，以满足 F-AUD 需求为准，阶段 9 通过评测选型 |
| 歌词/百科内容 | 正常使用在线歌词源与公开百科数据，标注来源即可 |
